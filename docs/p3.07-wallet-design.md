# P3.07 Intelligence: mako behind the gateway, with a wallet per Midgar ID

Status: design reviewed and approved by the main session on 2026-10-17 with two amendments (residual sweep in section 4, identity existence check in section 5). Built and deployed as of 2026-10-23: steps 1 to 6 (sections 10 and 11 say where the build differs). Built on branch `wt/p3.07-rest` and not deployed yet: steps 7, 9, 10 and 11 (section 12), all off or hidden until their secrets and flags are set. Not built: step 8 (hostname migration, an app release each). Decisions D2, D8, D11, D12 apply. Workers Free plan throughout (10 ms CPU, no new D1 database, no new cron trigger).

## Summary of decisions

1. The gateway binding already exists. Left: hostname migration (an app release each) and keeping `mako.midgarcorp.cc` alive for webhooks and old builds.
2. The wallet is a SQLite Durable Object class `Wallet` in the mako worker, one instance per Midgar ID, partitioned by `tenant` (mako's `apps.app_id`). A spend sees only its own tenant. A `sharing` switch is stored and hard-wired to `off` until P4.00.
3. Money moves only through an append-only `entries` table with a unique idempotency key; the per-tenant balance is derived in the same synchronous step.
4. mako verifies Midgar access tokens itself (JWKS over a new `IDENTITY` binding), from a new header `X-Midgar-Token`; the API key stays in `Authorization`.
5. Linking is a saga logged in a D1 `wallet_links` row; a D1 balance moves into the wallet once, keyed `migrate:<tenant>:<user>`. Never-upgraded users stay on D1 unchanged.
6. AI Gateway is a base-URL switch behind one variable, payload logging off; creating it is an `account` step. `api_keys` pruning runs in the existing cron; `users.api_key` goes via a nullable bridge rebuild, a code release, then `DROP COLUMN`.

## 1. Current model

### Tables (migrations 001 to 026)

- `apps` (`app_id`): tenant config (`new_user_free_credits`, `rc_project_id`, `rc_product_prefix`, `strict_purchases`, `store_prompts`, `art_credits`, ...).
- `users` (`id`, unique `(app_id, provider, provider_id)`): one row per person per app; anonymous users use the device key as `provider_id`. Holds `api_key` (placeholder `hashed:<id>`), `api_key_hash`, `is_admin`.
- `api_keys` (`key_hash`): per-device SHA-256 keys with `last_used_at`, refreshed hourly.
- `user_credits` (`(app_id, user_id)`): balance, `lifetime_purchased`, `lifetime_spent`. This is today's wallet: per tenant and per app user.
- `credit_transactions` (ledger with `balance_after`), `credit_purchases` (one row per external payment, looked up by `(app_id, payment_provider, payment_id)`), `credit_refunds` and `purchase_refunds` (claim rows), `realtime_sessions` (reservations).
- Not money: `user_locks`, `weekly_usage`, `chat_requests`.

Tenants use mako ids (`dreameater`, `payday`, `livingdex`, `doublekick`, `pixie`; the rest equal the slug). The Midgar access token's `app` claim is the registry slug (`dream-eater`, `pay-day`, `living-dex`, `double-kick`, `pixiepocket`), so section 4 adds a mapping.

Authentication: `auth::authenticate` reads `Authorization: Bearer <key>` and `X-App-ID` (default `pixie`), tries `api_keys`, then `users.api_key_hash`, then the legacy plaintext column (`api_keys::lookup_steps`), and returns `AuthedUser { user_id, app_id, is_admin }`. Every handler passes `(app_id, user_id)` to `credits.rs`.

## 3. Wallet design

`#[durable_object] pub struct Wallet` in `src/wallet/` of the mako crate (worker 0.6.7 has `State::storage().sql()`). worker-rs durable objects expose `fetch` only, so the "RPC" is JSON over `stub.fetch_with_request` on internal paths, typed by shared serde structs. wrangler config:

```toml
[[durable_objects.bindings]]
name = "WALLET"
class_name = "Wallet"
[[migrations]]
tag = "v1"
new_sqlite_classes = ["Wallet"]
[[services]]
binding = "IDENTITY"
service = "midgar-identity"
```

Free plan: SQLite-backed classes only, with 100,000 requests, 13,000 GB-s, 5M rows read and 100,000 rows written per day (https://developers.cloudflare.com/durable-objects/platform/pricing/). A metered request costs two DO requests (balance, spend) and about five rows written (entry, its two indexes, the balance row). Rows written binds first, at roughly 20,000 metered calls a day; 542 users are far below it. Revisit at 10,000 or move to the Paid plan.

### Schema inside each Wallet object

```sql
CREATE TABLE entries (
  seq           INTEGER PRIMARY KEY AUTOINCREMENT,
  idem_key      TEXT NOT NULL UNIQUE,
  tenant        TEXT NOT NULL,
  kind          TEXT NOT NULL CHECK (kind IN ('purchase','bonus','migrate','spend','refund','reversal','adjust','marker')),
  amount        INTEGER NOT NULL,
  balance_after INTEGER NOT NULL CHECK (balance_after >= 0),
  source        TEXT NOT NULL,
  reference     TEXT,
  description   TEXT NOT NULL,
  at            INTEGER NOT NULL
);
CREATE INDEX entries_tenant_seq ON entries(tenant, seq);

CREATE TABLE balances (
  tenant     TEXT PRIMARY KEY,
  balance    INTEGER NOT NULL CHECK (balance >= 0),
  purchased  INTEGER NOT NULL DEFAULT 0,
  spent      INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
INSERT INTO meta (key, value) VALUES ('schema', '1'), ('sharing', 'off');
```

`entries` is the truth; `balances` is derived (`balance = SUM(amount)` per tenant) in the same synchronous call, and `GET /verify` recomputes and compares. `amount` is signed. `source` is one of `revenuecat`, `stripe`, `crypto`, `apple`, `welcome`, `d1`, `admin`, `usage`, later `pass`. `marker` rows have amount 0 and only claim a key (the welcome claim).

Sharing later: the tenant column is already the partition. A future `sharing = 'on'` would let `spend` fall back to a reserved `*` pool after the caller's own tenant. That path does not exist today: `meta.sharing` is read nowhere and `tenant = "*"` is rejected with 400. Enabling it is P4.00's pricing decision plus a small Rust change, with no data move.

Idempotency keys: store purchase `tx:<store transaction id>` (shared by the RevenueCat webhook, the fast-track and the ledger, so they dedupe each other); `stripe:<purchase id>`, `crypto:<purchase id>`; `welcome:<tenant>`; `migrate:<tenant>:<app user id>`; spend `spend:<reference>` (the `chat:<uuid>` reference each handler already mints once); refunds `refund:<reference>`, `settle:<session id>`, `sweep:<session id>`; reversal `reverse:<store transaction id>`; admin `admin:<uuid minted once by the caller>`.

### Methods

```rust
pub struct Entry { pub key: String, pub tenant: String, pub kind: Kind, pub amount: i64,
                   pub source: String, pub reference: Option<String>, pub description: String }
pub enum Outcome { Applied { balance: i64, seq: i64 }, Replayed { balance_after: i64, seq: i64 }, Insufficient { balance: i64 } }
pub fn apply(books: &mut impl Books, entry: &Entry, now: i64) -> Result<Outcome, WalletError>;
pub fn migrate_amount(moved: i64, welcome_part: i64, welcome_marker_exists: bool) -> i64;
```

| Path | Behaviour | Status |
|---|---|---|
| `POST /grant` | Entry with positive amount, kinds purchase, bonus, refund, adjust. `Replayed` returns the stored result and never changes anything | 200 |
| `POST /spend` | Negative entry. Insufficient funds append nothing | 200, 402 `{balance}` |
| `POST /reverse` | Clamped debit for refund reversal and negative admin adjustments; returns `{taken, balance}` | 200 |
| `POST /migrate` | `{tenant, key, moved, welcome_part}`. See section 4 | 200 |
| `GET /balance?tenant=` | `{balance, purchased, spent}` | 200 |
| `GET /entries?tenant=&before=&limit=` | Newest first, for `/v1/credits/transactions` | 200 |
| `POST /erase` | `{tenant}` deletes that tenant's entries and balance (account deletion parity) | 200 |
| `GET /verify` | Recompute every tenant; ops tool, also run in tests | 200 |

A key reused with a different `amount` or `kind` answers 409 `idempotency_conflict`, except `migrate` (section 4).

### Concurrency

`apply` reads `find(key)` and the balance, inserts the entry and upserts `balances` with synchronous `sql.exec` calls and no `.await` between them. Input gates cannot interleave another request into a synchronous run, so two spends for one Midgar ID are strictly ordered and the second sees the first's balance. The `CHECK (balance_after >= 0)` constraints are a second wall: an overdraw fails the insert and writes nothing. There is no read-modify-write retry loop, unlike `deduct_credits_clamped` today.

`apply` and `migrate_amount` are written against a `Books` trait with an in-memory implementation, so `cargo test --lib` covers replay, insufficient funds, clamping, tenant isolation and the migration rule. A host-only dev-dependency (`rusqlite` with `bundled`, under `cfg(not(target_arch = "wasm32"))`, so the wasm `cargo check` is unaffected) also runs the real object schema and the D1 migrations through SQLite in the same test run.

### How mako calls it
```rust
pub enum Account {
    Local  { app_id: String, user_id: String },
    Wallet { midgar_id: String, app_id: String, user_id: String },
}

pub struct Ledgers<'a> { pub db: &'a D1Database, pub wallets: Option<ObjectNamespace> }

impl Ledgers<'_> {
    pub async fn balance(&self, a: &Account) -> Result<i32, AppError>;
    pub async fn spend(&self, a: &Account, charge: &Charge) -> Result<i32, AppError>;
    pub async fn grant(&self, a: &Account, grant: &Grant) -> Result<GrantResult, AppError>;
    pub async fn reverse(&self, a: &Account, key: &str, amount: u32, reference: &str) -> Result<(i32, u32), AppError>;
}
```

`AuthedUser` gains `account: Account`. The 25 call sites listed in section 1 change from `(&auth.app_id, &auth.user_id, ..., &db)` to `(&ledgers, &auth.account, ...)`; the old function names stay as thin wrappers so the diff is mechanical. `Account::Local` runs today's D1 code unchanged. `Account::Wallet` calls the object and then upserts a best-effort mirror row in D1 (below).

D1 mirror for reporting, since no query spans objects:
```sql
CREATE TABLE wallet_summary (
  app_id TEXT NOT NULL, midgar_id TEXT NOT NULL,
  balance INTEGER NOT NULL, purchased INTEGER NOT NULL, spent INTEGER NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (app_id, midgar_id)
);
```

Created in migration 030 and written after each wallet call from the returned balance; admin stats and search add it to the `user_credits` sums. Advisory only: no decision reads it and it can be rebuilt from `GET /verify`.

### Failure handling

- Spends and balance reads fail closed: DO error or timeout gives 503 `wallet_unavailable` with `Retry-After`. There is deliberately no fallback to D1. A linked user's D1 balance is frozen at zero, so a fallback could not spend anyway, and it would hide the outage.
- A spend after a successful provider call that then fails (DO down) behaves like today's failed `deduct_credits`: logged, the result is still returned, the shortfall is the price of the outage. The `check` before the provider call fails closed, which keeps that window small.
- Grants are retried idempotently by whoever delivered them: RevenueCat, Stripe and NOWPayments retry non-2xx; the fast-track returns the existing "will be credited shortly" error; the cron sweeps `credit_purchases` rows that are `pending`, `payment_provider = 'revenuecat'` and older than 5 minutes (limit 50) through `complete_purchase`. Stripe and crypto `pending` rows are legitimately waiting for payment and are left alone.
- Grant ordering changes for wallet accounts: insert the `credit_purchases` row as `pending`, call `/grant` (idempotent), then flip to `completed`. A crash in between leaves `pending`, which the retry finishes. No credit can be lost and none can be doubled.
- A failing D1 mirror write never fails a request. Account deletion (`DELETE /v1/identity`) adds `wallet_links` to `USER_DATA_TABLES` and calls `POST /erase` for that tenant only; deleting the Midgar ID itself is step 10.

## 4. Linking existing users

### Identifying the caller

A request may carry `X-Midgar-Token: <access JWT>` next to `Authorization: Bearer <api key>`. mako verifies it in `src/midgar_token.rs`:

- Keys: `GET https://identity.internal/.well-known/jwks.json` over the `IDENTITY` binding, cached 5 minutes per isolate, one forced refresh per minute on an unknown `kid`, last keys reused when identity is down (the same behaviour as `services/ledger/src/auth.ts`).
- Checks: `alg = ES256`, `iss = midgar-identity`, `aud = midgar`, `exp`, and `app` equal to the registry slug of the canonical `X-App-ID`. Signature through `SubtleCrypto.verify` (raw r and s, as the JWS carries them), so CPU stays under 10 ms; claim checks are pure and unit tested. Result: `MidgarCaller { midgar_id (lowercased sub), tier }`.
- `apps` gets `registry_slug` (migration 030). A bad or expired token on a request that also has a valid API key is ignored with a log line and the request proceeds on the API key alone, so a clock or JWKS problem never breaks an app that worked yesterday. A request with only a token and a bad token is 401.

A request with only `Authorization: Bearer <JWT>` (shape `eyJ...` with two dots) and no API key is a Midgar-ID-native request, used by MidgarKit 4 apps. Resolution: oldest `wallet_links` row for `(app_id, midgar_id)`; if none, create a `users` row (`provider = 'midgar'`, `provider_id` = Midgar ID, `api_key_hash` NULL), a link already in state `linked` with `moved_credits = 0`, and the welcome grant `welcome:<tenant>` only when `tier = app_attest` (D12: free grants need an attested device). Paid purchases work at any tier.

### D1 state added (migration 030)

```sql
CREATE TABLE wallet_links (
  app_id        TEXT NOT NULL,
  user_id       TEXT NOT NULL,
  midgar_id     TEXT NOT NULL,
  state         TEXT NOT NULL CHECK (state IN ('moving','linked')),
  moved_credits INTEGER,
  residue_moves INTEGER NOT NULL DEFAULT 0,
  residue_pending INTEGER,
  welcome_part  INTEGER,
  linked_at     TEXT NOT NULL,
  PRIMARY KEY (app_id, user_id)
);
CREATE INDEX idx_wallet_links_midgar ON wallet_links(midgar_id, app_id, linked_at);
ALTER TABLE apps ADD COLUMN registry_slug TEXT;
UPDATE apps SET registry_slug = CASE app_id
  WHEN 'dreameater' THEN 'dream-eater' WHEN 'payday' THEN 'pay-day'
  WHEN 'livingdex' THEN 'living-dex' WHEN 'doublekick' THEN 'double-kick'
  WHEN 'pixie' THEN 'pixiepocket' ELSE app_id END;
```

A user links to exactly one Midgar ID, ever (primary key). The same user presenting a different Midgar ID later is not re-linked: the request continues on the existing link and logs `wallet_link_mismatch`. The fix for a legitimately merged ID is the merge hook (step 11).

### The saga (`wallet::link::ensure_linked`), run on the first request that carries both a valid API key and a valid token, and by the cron for stuck rows

```rust
pub async fn ensure_linked(env: &Env, db: &D1Database, app_id: &str, user_id: &str, caller: &MidgarCaller)
    -> Result<Account, AppError>;
```

1. `INSERT OR IGNORE INTO wallet_links (..., state, linked_at) VALUES (..., 'moving', now)`. Read the row back. If `state = 'linked'` return `Account::Wallet`. If `midgar_id` differs: mismatch rule above.
2. Freeze, one D1 batch (a D1 batch is one transaction):
   - `UPDATE wallet_links SET moved_credits = (SELECT balance FROM user_credits WHERE app_id = ?1 AND user_id = ?2), welcome_part = (SELECT COALESCE(SUM(amount), 0) FROM credit_transactions WHERE app_id = ?1 AND user_id = ?2 AND type = 'bonus' AND description = 'Welcome bonus') WHERE app_id = ?1 AND user_id = ?2 AND moved_credits IS NULL`
   - `UPDATE user_credits SET balance = 0, updated_at = ?3 WHERE app_id = ?1 AND user_id = ?2 AND balance = (SELECT moved_credits FROM wallet_links WHERE app_id = ?1 AND user_id = ?2)`
   The second statement is a no-op on every rerun, and nothing adds to the D1 balance after step 1 because every credit path routes by the link row first.
3. `POST /migrate {tenant, key: "migrate:<tenant>:<user>", moved, welcome_part}`. Inside the object: if the key exists return the stored result; else `amount = migrate_amount(moved, welcome_part, marker_exists("welcome:<tenant>"))`, which is `moved` when no welcome has been claimed for this tenant and `moved - min(moved, welcome_part)` when one has; then insert the `welcome:<tenant>` marker if absent and the `migrate` entry. Both happen in one synchronous run.
4. `UPDATE wallet_links SET state = 'linked' WHERE app_id = ? AND user_id = ? AND state = 'moving'`.

D1 history stays as the archive; `/v1/credits/transactions` for a wallet account returns wallet entries, then older D1 rows.

Residual sweep (main-session review): a `Local` grant or refund already in flight when the freeze ran (a refund for a spend that started before the link, a webhook that resolved the account a moment earlier) lands in the frozen D1 row after step 2. The cron finds linked users whose `user_credits.balance > 0` (limit 20 per run) and moves the residue with the same freeze-then-migrate pattern under the key `migrate:<tenant>:<user>:<n>`, where `n` is the count of earlier migrate entries for that user, recorded in `wallet_links.residue_moves`; the frozen amount of a move in progress sits in `residue_pending` (set and the D1 balance zeroed in one batch, cleared with the `residue_moves` increment after the wallet answered), so a crash at any point replays the same key with the same amount. The welcome dedupe does not apply to residue. No credit is stranded in D1 for a linked user for longer than one cron interval.

### Crash analysis

D1 and the object cannot share a transaction, so `wallet_links` is the saga log and every step is idempotent.
| Crash after | State | Money | Recovery |
|---|---|---|---|
| step 1 | `moving`, `moved_credits` NULL | all in D1 | next request or cron reruns step 2 |
| step 2 | `moving`, `moved_credits = N`, D1 balance 0 | recorded only in the link row | rerun step 3 with the stored `N`; nothing else can spend it because every credit path checks the link first |
| step 3 | wallet holds the entry, link still `moving` | in the wallet | rerun step 3 gets `Replayed`, then step 4 |
| step 4 | `linked` | in the wallet | none |

While a link is `moving`, a metered request for that user completes the saga first and answers 503 if the object is unreachable. The cron resumes rows `moving` for more than 5 minutes (limit 20) without a token, since the row already carries the verified Midgar ID. A request authenticated as `Account::Local` that loses the race to the freeze gets a 402; the handler re-resolves the link once and retries through the wallet.

### Two app users, one Midgar ID, one tenant (reinstall)

Anonymous mako users are keyed by device key, so a reinstall makes user B beside the old user A, and both may link to the same Midgar ID. Rule: the wallet partition is `(midgar_id, tenant)`, both migrations land in it under distinct keys, and the welcome bonus is counted once. Real purchased credits of both users are kept because they are real money. The second migration subtracts its recorded welcome bonus (clamped at the migrated amount; spends are assumed to eat the welcome bonus first, the conservative choice). The same user linking twice is the same key and does nothing.

`weekly_usage` free buckets are not money, stay per user in D1, and are not deduplicated here.

Users who never upgrade have no token and no link: `Account::Local`, section 1's code unchanged, spending, buying and refunding in D1 as before, and migrating on a later link like any other balance.

## 5. New purchases

`credit_target(db, app_id, rc_app_user_id) -> Account` decides where a grant goes:

1. `wallet_links` has `(app_id, user_id = id)` in any state: `Account::Wallet`.
2. `users` has `(app_id, id)`: `Account::Local` (never upgraded).
3. The id is a UUID in `wallet_links` by `(app_id, midgar_id)`: `Account::Wallet` for that Midgar ID. If it is a UUID unknown anywhere, mako asks identity over the `IDENTITY` binding whether that Midgar ID exists (an internal lookup route added in step 6, answering only exists or not); only then is it `Account::Wallet` for that ID directly, so money is never granted into an ID nobody holds. An ID identity does not know is an error (the sender retries, and the log names the id prefix). MidgarCommerce sets RevenueCat's `appUserID` to the Midgar ID (P2.09), so a buyer who has not yet called mako still gets paid into the right partition.
4. Anything else: today's behaviour (error, the sender retries).

| Grant path | Local (D1) | Wallet |
|---|---|---|
| RevenueCat webhook (`credit_pack_from_event`) | unchanged | `credit_target`, key `tx:<transaction_id>`, `status = 'completed'` early-return check |
| RevenueCat fast-track `validate` | unchanged | token's Midgar ID is the RevenueCat customer id; key `tx:<purchase_token>` |
| Stripe webhook, crypto IPN, status polls | unchanged | linked user's wallet, key `stripe:<purchase id>` or `crypto:<purchase id>` |
| Refund reversal (`CANCELLATION`) | unchanged | `/reverse` with `reverse:<transaction_id>`, clamped to the partition balance |
| Admin adjust | unchanged | by the target user's account |
| Welcome bonus | `initialize_user_credits` | `welcome:<tenant>`, `app_attest` tier only |

Tie to the purchase ledger: StoreKit purchases carry `appAccountToken` = Midgar ID, and `services/ledger` stores every transaction (consumables included; they are only excluded from entitlements) keyed by `transactionId`. RevenueCat's `transaction_id` for the App Store is that same id, so `tx:<transaction id>` is one key across RevenueCat and the ledger. Step 9 below adds a ledger-fed grant (`POST /internal/wallet/grant` on mako, shared secret `WALLET_INTERNAL_SECRET`, 404 when unset) that resolves the pack from the product id with the existing `resolve_tenant_by_product`, applies the sandbox rule, and refuses accounts that are not linked (no double-credit window against D1's `revenuecat` provider rows). It stays off (`LEDGER_GRANTS = "off"`) until D2's condition to retire RevenueCat for credits is met; with both on, the shared key makes them idempotent against each other. The reverse (a refund) shares `purchase_refunds` and `reverse:<transaction id>` the same way (step 9b).

## 6. AI Gateway

Facts (Cloudflare docs, fetched 2026-10-17):

- URL shape `https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/{provider}` (https://developers.cloudflare.com/ai-gateway/get-started/). Only a gateway named `default` is auto-created, and only by the first authenticated request; any other id must be created first in the dashboard (AI > AI Gateway > Create Gateway) or with the API using a token with `AI Gateway - Read` and `AI Gateway - Edit` (https://developers.cloudflare.com/ai-gateway/configuration/manage-gateway/). With authentication on, provider-native endpoints need `cf-aig-authorization: Bearer <token>`.
- Free plan: AI Gateway is available on all plans, core features free; legacy log storage on Workers Free is 100,000 logs across all gateways (https://developers.cloudflare.com/ai-gateway/reference/pricing/). Gate (`account`): the gateway and its token need the dashboard. ## 7. api_keys pruning and the `users.api_key` rebuild

### Pruning (in `scheduled`, after the existing sweep and backfill)

```sql
DELETE FROM api_keys WHERE key_hash IN (
  SELECT key_hash FROM api_keys
  WHERE COALESCE(last_used_at, created_at) < ?1
  ORDER BY COALESCE(last_used_at, created_at) LIMIT 500
)
```

`?1` is `now - 180 days` as RFC 3339 (the stored format, which sorts as text). Migration 027 (`027_api_keys_last_used_index.sql`) adds `CREATE INDEX idx_api_keys_last_used ON api_keys(COALESCE(last_used_at, created_at))`. The batch cap keeps one cron run to a single bounded statement. Pruning never touches `user_credits`, wallets or `users`; a pruned device logs in again (anonymous re-registration finds the same user by device key and issues a new key, so the balance is intact). Legacy single-hash users (`users.api_key_hash`, no `api_keys` row) are unaffected. Pure part, `prune_cutoff(now) -> String`, gets a unit test beside `should_refresh_last_used`.

## 10. As built: steps 5 and 6

Branch `wt/p3.07-link`. Where the build differs from the text above, the build wins:

- **Flag off is local everywhere.** With `WALLET_LINKING` anything but `on`, no request reads `wallet_links`, so a user who was already linked is on its (zero) D1 balance again until the flag is back on. Their money is safe in the object. The reverse saga mentioned in section 8 is still not built, so the flag stays on once the first real user has linked.
- **Freeze is compare-and-swap.** Both statements of step 2, and of the residue freeze, only apply while `user_credits.updated_at` is the value that was read, and step 2 records `COALESCE(balance, 0)` so a user without a balance row links with nothing to move. A second concurrent run, or a credit of the same size landing between two runs, can no longer be swallowed by the second statement.
- **Object responses carry totals.** `grant`, `spend`, `reverse` and `migrate` answer with `balance_now`, `purchased` and `spent` (read in the same synchronous run) so the D1 mirror needs no second request; `GET /entries` answers `total`; `GET /entry?tenant=&key=` returns one entry (client refunds read the spend they refund from it).
- **Identity lookup secret.** `GET /internal/exists/<id>` on identity (`services/identity/src/exists.ts`) is guarded by its own `IDENTITY_LOOKUP_SECRET` in `X-Midgar-Internal`, set on identity and mako; 404 when unset. Only `active` identities exist; a merged-away ID does not.
- **A grant to an unknown but existing Midgar ID** creates a `provider = 'midgar'` user and a `linked` row first, because `credit_purchases.user_id` has a foreign key to `users`. Such a link has no welcome bonus.
- **Keys that must not repeat.** Legacy image charges and flat-capability charges without a caller-named `reference` get a fresh `spend:image:<uuid>` or `spend:<capability>:<uuid>` key, a named capability reference is keyed `spend:<capability>:<reference>`, and a client key whose free repeats are used up and which is charged again gets `spend:<reference>:<uuid>` (the D1 ledger charged it again; a repeated wallet key would not). An Apple merge credits under `merge:<anonymous user>:<uuid>` and puts the drained credits back on the anonymous row when a wallet cannot take them. A wallet charge with an empty reference is refused. The D1 ledger rows keep the references they always had.
- **Settled before addressed.** `Ledgers::account_for_user` finishes a `moving` link before it returns the wallet, so a refund reversal or an admin debit never runs against a wallet that does not yet hold the migrated balance; a local reversal that took less than asked re-resolves the link once and takes the rest from the wallet (`<key>:late`). A purchase completed through the local balance re-reads the link after it won the flip and, when the user linked meanwhile, credits the wallet under the purchase's key instead (releasing the claim if the wallet cannot answer), and a wallet completion re-reads the status before it grants, so a purchase is never credited in both places.
- **Native requests** are understood by every handler that authenticated by API key before, except the anonymous-to-Apple `link` call (`auth::authenticate_account`). The tenant named by `X-App-ID` must be a configured `apps` row, and the alias table is warmed for a token-shaped bearer without an `X-App-ID`.
- **Account deletion** erases the tenant partition of the Midgar ID, which also empties the partition other app users of the same Midgar ID (a reinstall) share.
- **Not done:** premium entitlement checks and ad-attribution tagging of subscriptions still look the buyer up by the app user id, so they need the Midgar ID too once apps set RevenueCat's `appUserID` to it.

## 11. As built: StoreKit 2 verification without RevenueCat

Branch `wt/p3.07-verify`. A credit pack bought through StoreKit 2 can be credited without RevenueCat: the client sends `signed_transaction` (the JWS of the purchase) next to `pack_id`, `purchase_token`, `product_id` and `platform`.

- **Ledger.** `POST /internal/verify-transaction` (`services/ledger/src/verifyRoute.ts`): secret `LEDGER_VERIFY_SECRET` in `X-Midgar-Internal` (404 when unset, 401 when wrong), body `{signedTransaction}`, verified with the same `verifyTransaction` as `POST /transactions`, answer `{transactionId, originalTransactionId, bundleId, productId, type, appAccountToken, environment, purchaseDate, revocationDate, inAppOwnershipType, quantity, registrySlug}`. It stores nothing. `registrySlug` is the registry app that owns the bundle id (null when none does); it is the one field beyond the spec, so mako can use the registry as the bundle's tenant mapping.
- **mako.** The validate route branches on a non-empty `signed_transaction` after the pack and product-prefix checks, and the RevenueCat path is otherwise unchanged. The caller's Midgar ID is the verified `X-Midgar-Token` or the native JWT (read even with `WALLET_LINKING` off). The transaction must have: a bundle id that is the tenant's registry app (`apps.registry_slug`) or its `apps.apple_app_bundle_id`; `appAccountToken` equal to the caller's Midgar ID; `productId` equal to the request's and resolving, by the longest `rc_product_prefix`, to a pack of this tenant; type `Consumable`; no `revocationDate`; ownership `PURCHASED`; quantity 1; and, for a `strict_purchases` tenant on the production worker, environment other than `Sandbox` (the webhook's rule). Then the credit goes through `record_pending_purchase` and `complete_purchase` under payment id `<transactionId>`, which is the grant key `tx:<transactionId>` of the wallet and the unique `(app, revenuecat, payment id)` row of D1, so the webhook, the RevenueCat fast-track and a replay all dedupe against it. With `WALLET_LINKING` on the account is `credit_target(midgar id)`, the one the webhook resolves; off, it is the caller's local account, and the grant is the D1 `complete_purchase`.
- **Codes.** `credit_pending` is **409** (not 202: a 2xx with an error body is decoded as a success by every client), with `Retry-After: 5`; it covers a ledger that cannot be asked (missing binding or secret, wrong secret, 5xx), an unreachable identity or wallet, and the three cases the RevenueCat path used to hide behind a 500. `already_processed` and `unverifiable_purchase` are 400 and keep the old texts (`Purchase has already been processed`, `Purchase could not be verified with RevenueCat`). A transaction of another app or Midgar ID is 403 `forbidden`; a verified transaction that is no creditable pack is 400 `bad_request`; no Midgar token at all is 401. 402 `insufficient_credits` carries `error.balance`, a number, whenever the failing check knew it.
- **Deploy order.** Ledger first (route is 404 until its secret exists), then mako with the `LEDGER` binding, then the app releases that send `signed_transaction`. Until the secrets exist on both workers a signed purchase answers `credit_pending` and RevenueCat's webhook credits it as before.

### Step 9: ledger-fed grants

- **mako** `POST /internal/wallet/grant` (`src/handlers/wallet_internal.rs`, logic in `src/wallet/ledger_grant.rs`). Needs `WALLET_INTERNAL_SECRET` in `X-Midgar-Internal` and `LEDGER_GRANTS = "on"` in mako's own vars; either missing is 404, a wrong secret 401. Body is the ledger's verified-transaction shape (the `LedgerTransaction` of `POST /internal/verify-transaction`). The tenant comes from the product id (longest `rc_product_prefix`), the transaction is held to the validate call's rules (`storekit::check`: bundle or registry slug, `appAccountToken` is the Midgar ID, product, consumable, not revoked, `PURCHASED`, quantity one, the strict-tenant sandbox rule), and the pack comes from `credit_packs`. Only a Midgar ID that a user is already linked to (`wallet_links`, any state) is credited, with `WALLET_LINKING` on; anything else is a 200 with `status: "refused"` and a `reason`, which the ledger treats as final. The credit is the one `credit_signed` makes: `record_pending` for the link's user, then `complete_in_wallet`, so the grant key is `tx:<transactionId>` and the `credit_purchases` row is the RevenueCat one `(app, revenuecat, transactionId)`; the webhook, the validate call and this route cannot credit a transaction twice, in either order, with a crash anywhere between (tests inject one after every write). A purchase row left `pending` by a crash is finished; one whose user is not linked is left to its own path (`credited_elsewhere`). Answers: 200 `{ok, status: credited|duplicate|refused, reason?, purchase_id?, credits?}`, 503 when the wallet cannot answer, 400 for a body that is no transaction.
- **ledger** `src/walletGrant.ts`. With `LEDGER_GRANTS = "on"` a `ONE_TIME_CHARGE` notification is forwarded after it is stored, and again when Apple redelivers it; a non-2xx answer, a thrown binding or a missing secret makes the ledger answer 503 `grant_pending`, so Apple retries. A transaction reported with `POST /transactions` is forwarded in `waitUntil` when it is a consumable bought within 24 hours and a failure only logs. Candidates are consumables with an `appAccountToken` and no `revocationDate`. Off, nothing is forwarded and no response differs.
- **Unlinked buyers.** A consumable bought by a Midgar ID with no linked user is refused here, as the design says. The client's validate call and the RevenueCat webhook still credit it through `credit_target`; once RevenueCat is retired for credits, the client's validate call is the path for a buyer who never linked.
- Two secrets, not one: this route can create credits, so it has its own (`WALLET_INTERNAL_SECRET`, ledger and mako) and identity's lifecycle secret cannot reach it.

### Step 9b: ledger-fed refunds

- **mako** `POST /internal/wallet/refund` (`src/handlers/wallet_internal.rs`, logic in `src/wallet/ledger_refund.rs`, shared helpers in `src/wallet/pack_refund.rs`). Same auth as the grant route: `WALLET_INTERNAL_SECRET` in `X-Midgar-Internal` and `LEDGER_GRANTS = "on"`, either missing is 404, a wrong secret 401, and with `WALLET_LINKING` off nothing is reversed. The body is the same `LedgerTransaction`; a refunded transaction has a `revocationDate`, which is expected. The transaction is refused (200, `status: "refused"`, final for the ledger) unless its product resolves by the longest `rc_product_prefix` to a tenant (`unknown_product`, `unknown_tenant`), the bundle or registry slug is the tenant's (`wrong_app`), the type is `Consumable` (`not_consumable`, so a subscription is never touched), the product is a pack of the tenant (`unknown_pack`), and the purchase's user is linked to a wallet (`not_linked`; a balance RevenueCat credited locally stays with the RevenueCat path). Without a `credit_purchases` row for `(app, revenuecat, transactionId)` the refund is only recorded (`status: "recorded"`, see below). A row still `pending` is finished with `complete_in_wallet` first. The route then claims the refund in `purchase_refunds`, reverses the pack's credits in the wallet with the clamped `/reverse` under `reverse:<transactionId>` (down to a zero balance, so credits already spent are not clawed back further), and marks the purchase `refunded`. Answers: 200 `{ok, status: reversed|duplicate|recorded|refused, reason?, purchase_id?, credits?, taken?}`, 503 when the wallet cannot answer.
- **Once per transaction across paths.** The RevenueCat `CANCELLATION` and `REFUND` path (`reverse_pack_refund` in `src/handlers/credits.rs`) uses the same helpers: the purchase lookup, the `purchase_refunds` claim, `reverse:<transactionId>` and the `refunded` flip. A purchase already `refunded` is a `duplicate` for the route, and a claim already written makes the RevenueCat path a no-op, so a refund that reaches both is reversed once in either order. The wallet replays a key it has seen, so a claim left by a crash is finished by the retry instead of reversing twice, and a failed reversal releases the claim it wrote. Tests inject a crash after every write.
- **ledger** `src/walletGrant.ts`, `src/notifications.ts`. A `REFUND` notification for a consumable with an `appAccountToken` is forwarded after it is stored, and again on redelivery, through the code `forwardGrant` uses (`forwardToMako`); a non-2xx answer, a thrown binding or a missing secret makes the ledger answer 503 `refund_pending`. `REVOKE` is not forwarded: Apple sends it only when Family Sharing access ends, and consumables cannot be shared. Off, nothing is forwarded and no response differs.
- **Refund before credit.** A refund for a transaction no credit path has seen (the grant is still retrying, or Apple delivered the notifications out of order) writes the `purchase_refunds` claim with no user and no credits, and the RevenueCat refund path does the same. Every credit path checks that claim before it records a purchase and refuses the transaction for good: the ledger grant answers `refused` with reason `refunded` (final for the ledger), the signed and the RevenueCat-verified validate calls answer 400 `refunded` (message "This purchase was refunded, so it is not credited."), and the RevenueCat purchase event is acknowledged without a credit. MidgarCredits treats any 400 whose code it does not know as final (`classify` in `MidgarCredits+Purchase.swift`: only `credit_pending`, `unverifiable_purchase` and `already_processed` are special, and the text fallbacks match "already been processed" and "could not be verified", which the `refunded` message avoids), so the receipt leaves the queue and `buy` throws `purchaseRejected`. A refund that finds the purchase `pending` finishes it and then reverses it, so a credit a crash left half done does not outlive its refund. Residual race: a credit that passed the claim check in the same few milliseconds in which a refund recorded its claim is not reversed.
- **Known gaps.** A `REFUND_REVERSED` notification (Apple undoing a refund) does not re-credit; left for a follow-up.

### Steps 10 and 11: deletion and merge hooks

- **Transport.** identity's existing outbox (`identity_outbox`, retried with backoff 30 seconds doubling to an hour, never dropped) carries the events: a `DELETE /me` queues `mako:delete:<id>` next to `delete:<id>`, and a merge queues `mako:merge:<from>` next to `merge:<from>`, in the same D1 batch as the change. Rows whose id starts `mako:` go to mako over a new `INTELLIGENCE` service binding (`openai-image-proxy`) with `WALLET_LIFECYCLE_SECRET`; the others go to the ledger as before. No identity migration. mako's routes: `POST /internal/wallet/erase_all {id}` and `POST /internal/wallet/merge {from, to}`, both guarded by `WALLET_LIFECYCLE_SECRET` (404 unset, 401 wrong), both working whatever `WALLET_LINKING` is, because the money stays in the objects.
- **Decision: when mako cannot answer, the deletion still stands.** The identity is deleted and the erasure queued in one batch, so deleting a Midgar ID is never refused or delayed because mako is down, and a crash cannot leave one without the other. The erasure is retried until mako answers 2xx. This is deliberately not mako's own `DELETE /v1/identity` rule (fail if the wallet cannot answer): that request has a client waiting to retry, an erasure queued by identity has nobody to ask. The cost is a window in which a deleted ID's already-issued access token still reaches a wallet that is about to be erased. Nothing is silently dropped: a missing secret or an unreachable binding is a failed attempt, so the rows wait and are visible as `identity_outbox` rows with a growing `attempts`.
- **Decision: the unverified sweep does not erase wallets.** A swept identity was abandoned, not deleted by its owner, and its wallet may hold credits bought with money; the sweep queues only the ledger's event. A swept ID's wallet stays, unreachable. Follow-up for the founder: either keep it so, or give the sweep a way to ask mako whether an identity holds credits before deleting it.
- **erase_all.** Gated on D1: an ID with no `wallet_links` and no `wallet_summary` row has no object and none is created (a sweep of abandoned identities must not create thousands of empty Durable Objects). Otherwise it erases the ID's wallet and every wallet merged into it (found through the `absorbed:<id>` markers in `meta`, deepest first, the ID's own last), marks each erased with a tombstone (`meta.erased`, every later write answers 409 `erased`, which the client maps to 503 `wallet_unavailable`), then deletes the ID's `wallet_links` and `wallet_summary` rows in one D1 transaction. Idempotent; a crash is finished by the retry because the links that say where to look are removed last. Not erased: the `users` rows and other per-user data of the linked app users (the app's own `DELETE /v1/identity` does that), and the wallet of a legacy app user who linked to the ID and whose link a mako account deletion already removed.
- **merge.** `lifecycle::merge` in `src/wallet/lifecycle.rs`, the object side in `src/wallet/absorb.rs`. (1) Find the wallet that holds the survivor's credits now, following `sealed_into` pointers; an erased one means the survivor was deleted and the merged-away wallet is erased instead (the ledger's rule for its claims). (2) `POST /seal {into}` on the merged-away wallet: it refuses every write with 409 `sealed`, which fixes its totals, and a repeat keeps the first target. (3) Settle sagas that had already put credits into the sealed wallet: a `moving` link whose `migrate:<tenant>:<user>` entry is in it becomes `linked`, a residue move whose entry is in it is finished; without this the saga would run again against the survivor, find no such entry, and move the same credits twice. (4) `POST /absorb {from, items}` on the survivor: one `merge:<from>:<tenant>` entry per tenant with a positive balance plus the marker `absorbed:<from>`, in one synchronous run after every check, so all tenants or none; a repeat finds the marker. A survivor that was itself merged away since still answers a repeat from its marker and points anything new at its own survivor, which the merge follows (at most eight hops). (5) One D1 transaction points the merged-away ID's `wallet_links` at the wallet that holds the credits and drops its `wallet_summary` rows, then the survivor's mirror is refreshed. The D1 change comes last, so a crash is finished by running the merge again, and a finished merge is a no-op because the gate (`wallet_links` or `wallet_summary` names the merged-away ID) is false. Merges delivered out of order, or twice, end in the same place; tests cover chains, the reverse order, a deleted survivor, a crash after every write, and the two sagas above.
- **Keys.** New and unique: `merge:<from midgar id>:<tenant>` (the Apple-link merge uses `merge:<anonymous user id>:<uuid>`, whose last part is never a tenant name), `absorbed:<from>` (a `meta` key, not an entry), `tx:<transactionId>` is shared on purpose.
- **Known gaps.** A request that carries only the merged-away ID's access token (no API key) is Midgar-ID-native; with no link left for that ID it creates a fresh user and link and meets the sealed wallet, which refuses writes (503) until the token expires and the app adopts the surviving ID that identity's merge response names. Requests that carry an API key follow the repointed link at once. A deleted ID's wallet can be recreated by a native request carrying a still-valid token until it expires (about the token lifetime); the tombstone only exists once an erasure has run.

### The linking rehearsal (`scripts/rehearse-linking.sh`)

Section 7's rehearsal, scripted, to run on arch before `WALLET_LINKING` is turned on. It exports production D1 to `~/.config/midgar/backups/mako-d1-<date>-p307-linking.sql` (umask 077, the export's stdout to `/dev/null` because it prints a presigned URL, stderr kept in a private temp file with URLs redacted), loads it into a throwaway local D1, optionally applies `--migration FILE`s while checking that every balance checksum is unchanged, queues a `moving` link for every user (users share synthetic Midgar IDs in groups of three across apps, which exercises the reinstall rule), starts `wrangler dev --local` with `WALLET_LINKING=on` and runs the scheduled handler until every link is `linked`, so the saga that runs is the production one. Pass criteria, each a check: `SUM(moved_credits)` equals the D1 balances before linking; the balances of the linked users are zero; `SUM(wallet_summary.balance)` and every `(app, Midgar ID)` partition equal the moved credits less the welcome bonuses the reinstall rule drops (computed in SQL from the link rows); the lifetime ledgers and the set of users did not change; `foreign_key_check` is empty; three more cron runs change nothing. Pending RevenueCat purchases in the copy are made young first, so the cron's purchase sweep cannot add credits to the sums. It never touches `.dev.vars` content (it moves the file aside and back) and takes `sha256sum` or else `shasum -a 256`. `--from-sql FILE` skips the export and `--make-fixture OUT.sql` writes a synthetic stand-in (the schema after every migration, dumped the way D1 exports it, then 28 made-up users). When links stay `moving` it prints the causes found in the server log, ids removed. First run on the production copy (2026-10-23): it failed on arch because the wallet stub was opened with `DurableObjectNamespace.getByName`, which that wrangler's local runtime lacks, so every wallet call was `WalletUnavailable`; the stub is now opened with `id_from_name` and `get_stub`, the cause of a failed wallet call is logged, and the cron resumes links no run has frozen before links a wallet already refused once, so a few refused rows cannot hold the batch of 20 forever.
